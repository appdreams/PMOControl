# Supabase migrations

Place forward-only SQL migrations in this directory, named with an ordered timestamp and a concise purpose, for example `20261026090000_create_tenant_memberships.sql`.

Every table and policy must follow the owning Spec and the cross-tenant/RLS ADRs. Review the migration for same-Tenant composite foreign keys, deny-by-default behavior, indexes, rollback/forward-fix strategy and data retention before applying it. Do not add application tables until their schema has been reconciled to the approved domain contracts.

Unapproved schema candidates belong in `supabase/drafts/`, outside the CLI migration path. Promote a draft here only after contract review and local/CI validation; never apply drafts directly.

The first migration, `20261026163821_restrict_rls_event_trigger_execution.sql`, hardens an existing DEV event-trigger function; it creates no application tables. The next two migrations create the initial Identity & Access schema and indexes; `20261026190349_enable_self_membership_context_read.sql` grants the minimal read path for current Tenant context. `20261026210156_provision_tenant_with_platform_grant.sql` adds the platform-authorized Tenant onboarding RPC and private versioned Tenant role presets. The project `PMO Control` is designated as development. Do not apply these migrations to preview or production without separate environment configuration and review. Database credentials are not committed, and local `psql` access is not configured.

`20261027132120_list_tenant_membership_boundary.sql` adds a read-only membership directory RPC. It rechecks active Tenant/membership, exact-scope `membership.view`, and explicit deny; its projection omits email and grants from non-Tenant scopes. `20261027134145_assign_tenant_role_with_ceiling.sql` adds the versioned permission-to-scope catalog and atomic Tenant-role assignment/audit. `20261027135220_invite_tenant_members_with_delegation.sql` adds ordinary member invitation issuance/acceptance with role delegation revalidation, hash-only tokens, seven-day expiry, manual link sharing, membership/grant/audit transaction and no e-mail delivery. `20261027135719_fix_invitation_grant_payload_validation.sql` uses PostgreSQL-compatible JSONB checks in the acceptance RPC. No Portfolio/Project invitation scope is enabled. All these migrations are applied to designated DEV.

`20261027154433_revoke_tenant_membership.sql` adds membership versions to the authorized directory and an atomic revoke RPC. It protects the last active Tenant Admin, rejects self-revocation and stale versions, closes same-Tenant grants, and appends an idempotent audit event. Applied to designated DEV; verified function definitions, empty `search_path`, and execute grants (`anon` denied; `authenticated` allowed). The UI does not revoke any account automatically.

`20261027155632_manage_tenant_membership_lifecycle.sql` adds the sensitive Tenant permission `membership.manage` to both administrator presets and an atomic, versioned suspend/reactivate RPC. Suspension keeps grants for future reactivation but the suspended membership cannot authorize access; the last active Tenant Admin and self-transitions are protected. Applied to designated DEV; positive transition smoke, ACL/search_path, unchanged advisor findings and zero residual test fixtures verified. The workspace UI exposes the reversible actions separately from revocation.

`20261027163212_portfolio_project_scope_foundation.sql` creates the initial Tenant-owned `portfolios`, `projects` and temporal `portfolio_projects` schema, adds resource IDs to `access_grants` through generated columns and same-Tenant composite FKs, and enables RLS while revoking direct table privileges. It intentionally adds no access policies or CRUD RPCs. `20261027163415_index_portfolio_project_foreign_keys.sql` indexes all new FK lookups, including audit actors. Both are applied to DEV. A rolled-back smoke transaction confirmed valid same-Tenant links/grants, rejected cross-Tenant references and confirmed direct API roles cannot access these tables. Security advisor reports expected closed-table RLS findings; performance advisor reports no unindexed FK on the new tables (one pre-existing private-schema FK remains).

`20261027165200_invite_members_at_resource_scopes.sql` adds exact-scope Tenant/Portfolio/Project invitation issuance and acceptance. It resolves active same-Tenant resources, requires Tenant-level `membership.invite`, filters each role to permissions applicable at the chosen scope, enforces the issuer's exact-resource delegation ceiling and revalidates it during acceptance. The resulting grant, invitation consumption, membership transition and audit are atomic. `20261027165727_list_delegable_invitation_scopes.sql` returns only scopes with at least one delegable system role to an authenticated authorized member. Both invitation migrations are applied to DEV and covered by `supabase/tests/resource_scope_invitation_smoke.sql`, which rolls back all fixtures.

`20261027175329_assign_resource_roles.sql` adds Tenant-scoped `membership.grant` to Tenant Admin and PMO Admin and an authenticated wrapper for atomic Portfolio/Project grant assignment. Only another active member and an active same-Tenant resource can be targeted; deny, self-assignment, Tenant Admin at resource scope, unknown role permissions and incompatible scopes fail closed. Grant/audit are idempotent together. `20261027175837_list_resource_grant_targets.sql` exposes only active same-Tenant resources to authorized administrators; `20261027180442_move_resource_targets_private.sql` moves its privileged query into the private schema and keeps a public `SECURITY INVOKER` wrapper. These migrations are applied to DEV; `supabase/tests/resource_role_assignment_smoke.sql` covers assignment, replay, list, cross-Tenant and deny with rollback. The API and workspace form exist; association management and manager transfer were implemented in subsequent migrations. Real second-member validation remains pending.

`20261027224138_revoke_scoped_access_grant.sql` adds a versioned, idempotent RPC and API route to revoke an allow grant at Portfolio or Project scope. It revalidates the active Tenant membership and Tenant-level `membership.grant` permission with explicit-deny precedence, locks the Tenant/grant, and atomically stores the revocation plus `access_grant.revoke` audit. `project_manager` grants remain exclusively managed by manager reassignment. Applied to DEV; the expanded `resource_role_assignment_smoke.sql` passed transactionally with rollback, covering revocation, audit, replay, mismatched payload, and manager-role guard. ACL checks confirmed the public wrapper is invoker, `anon` is denied, and `authenticated` is allowed.

`20261027181701_portfolio_project_read_create.sql` adds exact-scope Portfolio/Project list and create RPCs with `SECURITY INVOKER` public wrappers and private implementations. Tenant Admin receives `portfolio.create`; Portfolio creation additionally requires Tenant `membership.grant`, grants the creator `pmo_admin` at that Portfolio only, and appends audit atomically. Project creation requires `project.create` on the active Portfolio, creates the same-Tenant association, grants the actor `project_manager` at the new Project, and audits atomically. The migration is applied to DEV and `supabase/tests/portfolio_project_read_create_smoke.sql` validates authorization, idempotency, initial grants, association and cross-Tenant rejection inside a rolled-back transaction. Update/archive and separate association management were implemented in subsequent migrations.

`20261027183256_update_archive_resources.sql` adds versioned update/archive RPCs for Portfolios and Projects and returns `canEdit`/`canArchive` in the authorized resource lists. Each mutation requires the matching exact-scope grant, expected version, reason and idempotency key, and writes the resource update plus audit event atomically. A Portfolio cannot be archived while an associated Project is active; Project archive sets `archived_at` without changing its workflow status. Applied to DEV; `supabase/tests/portfolio_project_read_create_smoke.sql` passed with rollback for update, idempotent replay, stale version, Project archive and subsequent Portfolio archive. Public functions are `SECURITY INVOKER`; privileged implementations remain in `private`.

`20261027184547_manage_portfolio_project_associations.sql` adds authorized Project targets and temporal link/unlink RPCs. Link/unlink require exact Portfolio permissions; the target also requires exact `project.view`. Unlink checks association version and writes audit/idempotency atomically while retaining the Project and historical link. PMO Admin presets receive the two sensitive association permissions. Applied to DEV; advisors show no new security finding. `20261027185024_fix_stale_association_conflict.sql` orders version validation before active-link validation so stale removals return a conflict while current-version requests against removed links remain denied. The transactional association smoke passed with rollback.

`20261027191449_assign_project_manager.sql` adds the exact-Project `project.assign` flow. It returns minimal active-member candidates, transfers `projects.project_manager_id`, revokes the prior active `project_manager` grant, grants the new manager and records one idempotent audit event atomically. Smoke in `supabase/tests/portfolio_project_read_create_smoke.sql` passed with rollback for candidate selection, two-member transfer, replay, stale-version rejection and the unchanged resource workflows. Lint and typecheck passed. The second Auth account is confirmed with active membership. The approved DEV fixture `Validação de troca de gerente` was created, and the second account received `pmo_admin` at exact Project scope with an audit event. The follow-up `20261027203631_prevent_noop_project_manager_assignment.sql` excludes the current manager from candidates and rejects no-op assignments. A stale-version conflict refreshes the project and candidate list in the UI. The current manager must still be changed by an authorized actor to a different active Tenant member; the third account has not accepted an invitation yet.

`supabase/seed.sql` contains the `rbac-v1` permission catalog and the two global platform-role presets. It is data-only and idempotent; it does not expose catalog tables through the Data API. Tenant role presets are created for each real Tenant by the onboarding flow, not as global rows without a Tenant. To reproduce the catalog on hosted DEV after reviewing pending migrations, use `supabase db push --linked --include-seed`; do not use `db reset --linked`.

`20261027205134_require_user_display_names.sql` guarantees a profile row and non-empty display label for existing and newly created Auth users. Names from Auth metadata are presentation hints only; when absent, the email local part is a temporary label and `profile_complete=false` prompts the user to set their own name. The `get_my_profile`/`update_my_profile` RPCs expose only the caller's profile, and the workspace updates its member list after save. Applied to DEV.

The first DEV platform operator is a separate manual bootstrap operation, not a migration or general-purpose endpoint. Follow `supabase/operations/bootstrap-first-platform-admin.sql` only after reviewing its target account, project ref, and one-time guards.
