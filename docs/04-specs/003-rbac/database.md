# SPEC-003 — RBAC & Contextual Authorization — Database

**Status:** MVP authorization schema applied in DEV; broader product-specific permission surfaces remain future scope

Canonical tables: `roles`, `permissions`, `role_permissions`, `access_grants`, `memberships`. MVP roles are platform-managed templates materialized per Tenant; custom role creation/editing is out of scope. Platform roles are global (`tenant_id IS NULL`, `scope_type='platform'`); Tenant role rows belong to exactly one Tenant (`tenant_id NOT NULL`, `scope_type='tenant'`). An `access_grants` row assigns one role to one subject in one scope; it is not a direct permission grant. Fields: `tenant_id, subject_id, role_id, scope_type, scope_id, effect, granted_by, reason, starts_at, expires_at, revoked_at, version`. Effective permission grants are a derived evaluation view: expand each active role assignment through `role_permissions`, then apply explicit denies before allowing a permission. System/platform grants use a null Tenant only for platform scope; every Tenant-scoped grant carries its Tenant ID. Tenant Admin cannot assign platform roles.

Constraints: `effect IN ('allow','deny')`; scope types are `platform|tenant|portfolio|project|resource|item`; role/scope/Tenant consistency; `expires_at IS NULL OR expires_at > starts_at`; immutable issuer/reason after creation except controlled revocation metadata. Platform role assignments require `tenant_id IS NULL`, `scope_type='platform'`, and `scope_id='platform'`; Tenant roles require a Tenant ID and cannot use platform scope. Use `CREATE UNIQUE INDEX ... ON access_grants (tenant_id, subject_id, role_id, scope_type, scope_id, effect) NULLS NOT DISTINCT WHERE revoked_at IS NULL`; this prevents duplicate active assignments even for platform rows and permits an explicit deny alongside an allow. The evaluator expands role permissions before applying deny precedence across matching resource ancestry. Permission catalog and inheritance edges are deployed/versioned with application, not user-editable; no implicit inheritance is introduced by the database. The initial application catalog is `rbac-v1` in `apps/web/src/modules/identity/domain/permission-catalog.ts`; `apps/web/src/modules/identity/application/prepare-tenant-role-presets.ts` prepares deterministic, Tenant-scoped rows for the trusted onboarding transaction. The planner does not authenticate or persist; presets are not assigned to users.

Platform authorization is evaluated separately from Tenant membership because platform actors need not belong to a customer Tenant. The pure evaluator in `apps/web/src/modules/identity/domain/platform-authorization.ts` checks platform scope, validity windows and explicit deny. Tenant creation is enforced independently in `private.provision_tenant`: it derives `auth.uid()`, checks the live platform grant and deny rows in the transaction, then materializes the versioned private preset rows. The exposed `public.provision_tenant` wrapper is SECURITY INVOKER; execution is granted only to `authenticated`. The private helper is SECURITY DEFINER with an empty search_path, exact grants, and no API exposure. No membership is implicitly assigned to the platform operator.

Indexes: `(tenant_id,subject_id,revoked_at,expires_at)`, `(tenant_id,scope_type,scope_id)`, role-permission lookup. RLS derives the actor from verified `auth.uid()` and checks current membership/Tenant state. The private versioned `permission_scope_catalog` (rbac-v1) supports Tenant, Portfolio and Project role assignments; each transaction locks the active Tenant/resource and issuer/subject memberships, requires exact-scope authority, checks proposed permissions against active allows/denies, and inserts grant plus audit atomically. Audit idempotency binds replay to actor/reason/payload. Unknown permission keys fail closed. Authorization decision cache is non-authoritative and invalidated on membership/grant/policy changes.
