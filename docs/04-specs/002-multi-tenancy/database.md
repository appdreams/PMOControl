# SPEC-002 — Multi-Tenancy — Database

**Status:** MVP Tenant, membership, invitation and export schema applied in DEV; extended product tables remain separately scoped

Tables: `tenants(id,slug,display_name,status,version,created_at,created_by,suspended_at,termination_started_at)` with status `active|suspended|termination_pending|export_ready|purging|terminated`; `memberships(id,tenant_id,user_id,status,created_at,activated_at,revoked_at,version)` with status `active|suspended|revoked`, unique `(tenant_id,user_id)`; `tenant_invitations(id,tenant_id,invitation_kind,email_normalized,grant_payload,token_hash,expires_at,accepted_at,revoked_at,created_by)` where `invitation_kind` is `first_admin|tenant_member`; export records are `tenant_exports`, `tenant_export_disputes` and `tenant_export_holds` (defined below); `tenant_quotas(tenant_id,plan_key,limit_key,limit_value,effective_at,updated_by)`.

Invitation `grant_payload` schema v1 is `{ "schema_version": 1, "grants": [{ "role_id": "<uuid>", "scope_type": "tenant|portfolio|project|resource|item", "scope_id": "<uuid>" }] }`. It contains role assignments only (implicit `effect=allow`), no direct permission keys or arbitrary caller data. Acceptance revalidates every role, Tenant and scope against current catalog/issuer delegation before creating grants; unknown fields/schema versions are rejected. Role templates are the platform-defined MVP presets materialized for the target Tenant; custom role editing is excluded.

Tenant provisioning materializes the seven Tenant-scoped system presets and their `role_permissions` from the application-owned catalog version inside the same transaction that creates the Tenant. `private.tenant_role_preset_permissions` stores versioned preset definitions outside the exposed Data API. The trusted onboarding RPC checks the live platform grant in the transaction and is idempotent by caller-supplied UUID recorded in a platform-scoped audit event; a repeated key with another actor or payload fails closed. Creating preset rows does not assign any role to a user. The first administrator receives a scoped grant only through an authorized invitation/acceptance flow. The current `roles` schema does not persist the catalog version on each materialized role.

`tenant_exports(id,tenant_id,requested_by,contact_user_id,status,artifact_bucket,artifact_path,artifact_sha256,artifact_bytes,manifest,schema_version,requested_at,generated_at,available_at,first_downloaded_at,notified_at,purge_after,completed_at,failure_code,idempotency_key,version)` stores only artifact metadata. `tenant_exports_contact_same_tenant_fk` binds the authorized contact to a membership in that Tenant. The artifact lives in private Storage bucket `tenant-exports`; only a server-side worker may write it, clients have no Storage write policy, and authenticated downloads require the designated active contact, a ready export and Tenant `export_ready`. A verified `available_at` sets `purge_after = available_at + 90 days`; metadata is not directly exposed through the Data API.

`tenant_export_disputes(id, tenant_id, tenant_export_id, filed_by, reason, disputed_scope JSONB, status, resolution, resolved_by, filed_at, resolved_at, version)` is the canonical dispute table. Composite FK `(tenant_id,tenant_export_id)` references `tenant_exports(tenant_id,id)`; `filed_by` must be an authorized export contact in the same Tenant; reason is non-empty; status is `open|resolved|rejected`; resolution requires actor, reason and timestamp. An open dispute pauses purge only for its recorded scope. Indexes cover `(tenant_id,tenant_export_id,status)`, `(tenant_id,status,filed_at)`, `filed_by` and `resolved_by`.

`tenant_export_holds(id,tenant_id,tenant_export_id,scope,reason,applied_by,applied_at,release_reason,released_by,released_at,version)` records scoped holds and their audited release. A null `tenant_export_id` denotes a Tenant-wide hold. Active holds are never removed by a purge. Migration `20261028004832_create_tenant_export_records.sql` creates these tables, closes direct privileges, creates the private bucket and installs the contact download policy; `20261028004947_index_tenant_export_foreign_keys.sql` adds reference indexes. The DEV smoke `tenant_export_storage_smoke.sql` passed with rollback. Artifact generation/finalization, dispute/hold commands and purge are not yet implemented.

Tenant admin transfer has no independent mutable table: execute as an idempotent command with `expected_version`, change Membership/AccessGrant in the same Tenant and append the `TenantAdminTransferred` audit/event in the same transaction.

Use composite FKs/constraints to prevent cross-tenant relationships. Normalize invitation email by trim + lowercase; store only SHA-256 of a cryptographically random 256-bit raw token, with expiry seven days after issue. The first-admin flow marks `invitation_kind='first_admin'`; member invitations mark `tenant_member`. Each issuance revokes only its own previous pending kind/address as appropriate and returns the raw token once in a URL fragment for manual sharing; no email is sent. Migration `20261027135220_invite_tenant_members_with_delegation.sql` adds member issuance and acceptance RPCs. Issuance requires active Tenant/membership, exact `membership.invite`, system Tenant role, every role permission delegable at exact Tenant scope and no deny. Acceptance locks Tenant and memberships before invitation, checks confirmed Auth email, rechecks the issuer's active membership/invite grant/delegation ceiling and permission scope catalog, then atomically consumes the invitation and creates/reactivates Membership plus scoped Role assignment/audit. Suspended membership cannot be reactivated; revoked membership can only return through a valid invitation. `purge_after` is set only after export is available; legal hold blocks execution. Tenant state transitions are constrained/audited. RLS derives actor from verified `auth.uid()` and validates current membership/Tenant state; platform lifecycle operations use a separately reviewed privileged service boundary with actor audit. Export artifacts are private/encrypted and removed under retention policy.

Migration `20261027154433_revoke_tenant_membership.sql` augments the authorized member directory with a string version and adds an atomic Tenant revocation RPC. It locks Tenant/memberships, validates `membership.revoke` and deny, protects the last active Tenant Admin, closes all grants for the target within that Tenant, and appends an idempotent audit event. Migration `20261027155632_manage_tenant_membership_lifecycle.sql` adds `membership.manage` and an atomic suspend/reactivate RPC that preserves grants during suspension, protects the last active Tenant Admin and records reason/version in audit. Applied to DEV; positive suspend/reactivate smoke passed in a transaction rolled back after checking status, version, retained grant and two audit events.
