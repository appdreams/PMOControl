# SPEC-002 — Multi-Tenancy — Business Rules

**Status:** Draft — MVP decisions incorporated

- Only the platform team can create, suspend/reactivate or start termination of a Tenant; each operation requires an authorized individual, reason and audit event.
- Tenant status is `active|suspended|termination_pending|export_ready|purging|terminated`; only `active` permits normal business operations. `suspended` blocks writes/integrations/jobs; `termination_pending` blocks normal use and begins export workflow. Export/purge states permit only their named lifecycle commands.
- Membership status is `active|suspended|revoked`. A pending invite is represented only by `tenant_invitations`; acceptance creates or reactivates the membership and grants in the same transaction.
- Tenant `slug` is generated from `display_name` by the platform: trim, Unicode NFKD normalize, remove combining diacritic marks, lowercase, replace each run of non-ASCII letters/digits with one hyphen, trim edge hyphens, truncate to 63 characters and trim a trailing hyphen. Names that yield fewer than three ASCII letters/digits are rejected. Slugs are deterministic and unique; collisions return conflict, without an automatic suffix or partial Tenant creation.
- Tenant transitions are restricted to `active → suspended|termination_pending`, `suspended → active|termination_pending`, `termination_pending → export_ready`, `export_ready → purging`, and `purging → terminated`. `purging` is forward-only and `terminated` is terminal. A hold or valid export dispute pauses purge without reversing Tenant state. Each command requires platform authorization, reason, row lock/version check and one atomic audit event. Invalid or stale transitions fail without partial writes.
- Membership transitions are `active → suspended|revoked`, `suspended → active|revoked`, and `revoked → active` only through a fresh, verified invitation acceptance. Direct reactivation of a revoked membership by an admin is prohibited. Every transition requires an authorized actor, reason where administrative, optimistic version/row lock, and atomic audit. Membership and grants are rechecked in the transaction that performs a protected mutation, so concurrent suspension/revocation serializes against that mutation.
- Membership revocation is Tenant-scoped and requires `membership.revoke`, an active Tenant and actor membership, an expected membership version, a reason, and atomic audit. A user cannot revoke their own membership through the administration UI/API, and the last active Tenant Admin cannot be revoked. Revocation closes all unrevoked grants belonging to that user in the same Tenant; it does not delete the membership or Auth account.
- Membership suspension/reactivation is Tenant-scoped and requires `membership.manage`, active Tenant/actor membership, expected version, reason and atomic audit. Self-transition is prohibited; the last active Tenant Admin cannot be suspended. Suspension retains grants (membership status blocks access); reactivation restores the same grants. Revoked memberships cannot be reactivated through this operation and require a fresh verified invitation acceptance.
- Users may hold memberships in several Tenants and choose one after login; selected context never substitutes for rechecking active membership.
- Invitation email is normalized to lowercase after trimming and bound to the intended Tenant. Generate a cryptographically random 256-bit token, store only its SHA-256 hash, and show the raw token once in the provider invite link. Expiry is exactly 7 days; accepted, expired, or revoked tokens cannot be reused. Reissuing an invite revokes prior unaccepted invites for the same normalized email and Tenant.
- Accept only after Supabase Auth confirms the user's email is verified and matches the normalized invite email. Consume with one conditional update (`accepted_at IS NULL`, `revoked_at IS NULL`, `expires_at > now()`) inside the same transaction that creates/reactivates Membership and assigns the invite's role/scope. Recheck the issuer's delegation ceiling at acceptance; parallel replay can commit at most once.
- The first Tenant administrator may be invited only by its active creator with a current `tenant.lifecycle.create` platform allow and no matching deny. This bootstrap invite grants only the system `tenant_admin` role, while no first administrator is active. Reissue revokes the prior pending link. The invitee must have an Auth account with a confirmed matching email. The app presents a one-time link for manual sharing and does not send email.
- Cross-tenant relations, reads, exports, storage access, AI grounding and background jobs are denied.
- Termination is export-first. The 90-day purge window starts only after export is generated and made available; legal hold/retention obligation suspends purge for covered scope.
- No fixed tenant/user cap in MVP; explicit plan quotas are configured by platform and enforced consistently.
- User-level hard delete is prohibited for governed entities; retention/purge is controlled by platform workflow and audit.
- Primary administration transfer requires an authenticated request from a current Tenant Admin and confirmation by the new administrator. If no active administrator can act, Platform Support uses JIT access with a ticket, independent approval, minimal scope, expiry and audit; the platform never silently transfers customer ownership.
- The export contact has 30 calendar days after availability notification to file a reasoned completeness dispute. A valid dispute pauses purge only for the disputed data scope until a resolution is recorded. No dispute does not extend the default 90-day purge window.
